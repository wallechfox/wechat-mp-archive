# v1.5 重构记录：模式分派层 + 共享采集器

- 版本：v1.5
- 日期：2026-10-30
- 改动文件：`app.py`（+172/−155）、`templates/index.html`（+52/−82）、`README.md`
- 性质：纯内部重构 + 死代码清理，**对外接口与导出结果不变**

## 1. 为什么要重构

重构前，“这次该用哪套凭证、走哪个数据源”这件事在两个 worker 里各写了一遍，而且都是靠**凭证是否存在**隐式判断的：

```python
# export_worker / fetch_articles_worker 里各有一份
use_mp_source = bool(token and mp_cookie)   # 填了后台凭证就当模式1
```

由此带来的实际问题：

| 现象 | 根因 |
|---|---|
| 扫码登录公众号后台后切到「模式 2」，仍去拉自己号的文章列表 | 判断依据是「有没有 token+mp_cookie」，而不是用户当前选的模式 |
| 模式 2/3 导出的文件夹被命名成自己的公众号名 | 前端 `gather()` 无条件下发 `mp_name=currentMpName`，后端直接拿来做目录名 |
| 模式 3 的链接列表被误判成模式 1 数据源 | 同上，凭证存在即走后台通道 |
| 改一处漏一处 | 同一段判断分散在 `fetch_articles_worker` 与 `export_worker` 两处 |

另外还有两处早就没人调用的残留：

- 后端 `POST /api/resolve`、`POST /api/comments`（v1.4 起评论改走 `comment_id` 直连后已无调用方）；
- 前端「评论详情」卡片、`showArticle()` / `doFetchComments()` / `renderComments()` / `doExport()`（“导出全部文章”按钮已移除，函数仍留着）。

## 2. 后端改动（`app.py`）

### 2.1 新增模式分派层（`app.py:2140` 起）

所有“用哪套凭证 / 走哪个接口”的判断收敛到这一层，worker 只做调度：

```python
MODE_MP = "1"       # 公众号后台
MODE_WEREAD = "2"   # 微信读书
MODE_LINK = "3"     # 链接直抓

def resolve_mode(cfg) -> str:        # app.py:2152
def mp_credentials(cfg) -> dict:     # app.py:2160  token/fingerprint/mp_cookie
def weread_cookie(cfg) -> str:       # app.py:2170
```

- `resolve_mode()` 以请求里的 `mode` 为准；旧前端没带 `mode` 时按凭证推断兜底（有 `token`+`mp_cookie` → 模式1，否则模式2），保证老页面不至于直接报错。
- `mp_credentials()` 把凭证读取收成一处：必填 `token` + `fingerprint`，缺一个就返回空 dict，调用方用 `if not cred` 判断，不再各自 `cfg.get(...)`。
- `weread_cookie()` 让“微读 Cookie”只在一个地方取值——模式1 也会用到它（正文的微读兜底），但不再和 `mp_cookie` 混在一起判断。

### 2.2 共享采集器（两个 worker 共用一套）

| 函数 | 位置 | 职责 | 返回 |
|---|---|---|---|
| `collect_mp_articles()` | `app.py:2175` | 模式1 文章列表：优先「发表记录」`appmsgpublish`，失败回退「原创」`appmsgcopyright` | `(articles, mp_name)` |
| `collect_weread_articles()` | `app.py:2213` | 模式2：`resolve_book_id` + 分页拉列表，必要时用列表回填公众号名 | `(articles, mp_name, book_id)` |
| `take_selected_articles()` | `app.py:2234` | 导出“选中文章”时不重拉列表，只补齐目录命名所需的名称/bookId | `(articles, mp_name, book_id)` |

细节：

- **回退逻辑不再吞掉“用户点了停止”**：`collect_mp_articles()` 里 `except TaskStopped: raise` 先于 `except Exception`，否则停止操作会被当成“发表记录失败”而触发一次原创列表回退。
- **名称隔离**：`take_selected_articles()` 里“我的号”名称（前端带来的 `mp_name`）**只在模式1 生效**；模式2/3 用本次拉列表解析出的目标公众号名，再不行退到目标 `bookId`，避免别人的号被导出成自己号的文件夹名。
- **统一三元组签名**：原来模式1 返回二元组、模式2 返回三元组，worker 里得写两套解包；现在两个采集器都由调用侧统一成 `articles, mp_name, book_id`。

### 2.3 两个 worker 变薄

`export_worker()`（`app.py:2262`）：

- 开头一次 `mode = resolve_mode(cfg)`，后面不再出现 `token`/`mp_cookie` 之类的分派判断；
- 模式3 直接报错并指向正确入口：`模式3（链接直抓）请走 /api/reader_export，不经过本接口`；
- 评论凭证只在模式1 才取，且用 `mp_credentials()`：模式2/3 明确记一行日志 `模式N 不抓评论（仅模式1 支持），本次仅导出正文`，不再出现“勾了评论却静默没有”的情况（v1.4 定的“评论不静默丢失”原则沿用）。

`fetch_articles_worker()`（`app.py:3012`）：

- 一次分派到采集器；模式3 给出明确提示（该模式不需要列表）；模式2 在日志里标注“（忽略公众号后台凭证）”，让“为什么没走后台”一眼可见；
- 时间范围日志、`on_page` 增量渲染、`CACHE` 回写统一收尾，两个分支不再各写一份。

### 2.4 补全文章短链不再拖住列表

模式2 的“补全短链”约 1 篇/秒，原来整段跑在拉列表任务里，用户得等全部补完才能点“下载选中”。现在：

- 列表一就绪就把 `task["articles_sofar"]` / `task["result"]` 交出去，并把状态切成 `enriching`；
- 补全过程中抛出的异常降级为 `[警告] 补全链接失败：…（不影响下载）`，`TaskStopped` 仍然向上抛，停止按钮照旧有效。

### 2.5 删除死接口

- 移除 `/api/resolve`（`resolve_book_id` 已由 `collect_weread_articles()` 内部调用）；
- 移除 `/api/comments`（v1.4 起评论走 `comment_id` 直连，前端早已不调）。

## 3. 前端改动（`templates/index.html`）

| 改动 | 说明 |
|---|---|
| `gather()` 带上 `mode` | 后端据此分派，不再猜 |
| `mp_name` 只在下发时区分模式 | `mp_name: currentMode === '1' ? currentMpName : ''`，从源头断掉“别人的号被命名成自己的号” |
| `pollFetchTask()` 支持 `enriching` | 新增 `fetchReleasedEarly` 标记，列表一就绪就放开按钮；`done` 阶段若已提前放行，只把补到的 `url` 合并回现有条目，**不覆盖**已下载/已移除的条目状态 |
| `switchMode()` 清理跨模式状态 | 切出模式1 时清空 `currentMpName` / `currentBookId`，同时清掉「当前公众号」提示，避免串号 |
| `pollLogin()` 不再自动填 `keyword` | 原来登录后台后会把**自己的** `book_id` 填进模式2 的“目标公众号”输入框，切到模式2 就会默认去拉自己的号 |
| 删除死代码 | 「评论详情」卡片 `#commentCard`、`showArticle()`、`doFetchComments()`、`renderComments()`、`doExport()` |

## 4. 行为变化对照

| 场景 | v1.4 | v1.5 |
|---|---|---|
| 登录后台后切模式2 | 可能仍走后台数据源 | 严格走微信读书，日志注明忽略后台凭证 |
| 模式2/3 的输出目录名 | 可能变成自己的号名 | 用目标公众号名，取不到退 `bookId` |
| 模式2 补全短链时 | 按钮全程锁定，等补完 | 列表就绪即可下载，链接后台补，补完合并 |
| 补全短链失败 | 整个拉列表任务失败 | 仅警告，列表与下载不受影响 |
| 模式2/3 勾了“导出评论” | 静默无评论 | 日志明确“仅模式1 支持” |
| 旧前端（不带 `mode`） | — | 按凭证推断，保持可用 |

## 5. 验证方式

1. 语法：`python -m py_compile app.py`；前端抽出 `<script>` 内容后 `node --check`。
2. 单元级回归（临时脚本，未入库）：分派正确性（三种 `mode` → 对应采集器）、凭证隔离（模式2 带后台凭证不误走后台）、目录命名（模式2/3 不取自己的号名）。
3. 链路回归：模式1「发表记录 → `comment_id` 直连评论」保持可用；模式2 拉列表 + 补全链接 + 直访回退；模式3 导入列表 → 勾选下载。
